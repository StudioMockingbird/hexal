# RFC 0040: Input and Output

- Kind: Feature Specification (Rust-Style RFC)
- Status: Implemented; conformance verified 2026-08-12
- Features: synchronous files, standard input/output, binary and UTF-8 I/O,
  explicit cleanup, buffering, and recoverable ordinary I/O errors
- Created: 2026-08-11
- Revised: 2026-08-11
- Depends on: RFC 0008 (calls and evaluation), RFC 0018 (String and Byte), RFC
  0020 (List and View), RFC 0022 (ADTs), RFC 0023 (truthiness), RFC 0024
  (equality, ordering, and hashing), RFC 0026 (defer), RFC 0029 (Error and try),
  RFC 0030 (`print` and the standard-output gate), RFC 0035 (manual lifetimes),
  RFC 0036 (`Size`), and RFC 0044 (text conformance cleanup)
- Coordinates with: RFC 0031 (`Stream<T>`), RFC 0037 (concurrency), RFC 0039
  (C interop), RFC 0043 (pointer-plus-length Views), and future Path, socket,
  and platform-library specifications

## Summary

V1 provides a small synchronous File API built primarily on C23 stdio:

```seawitch
file: File = try File.open("notes.txt", FileMode.Read)
defer file.close()

text: String = try file.read_text(h)
defer text.free(h)
print(text)
```

File owns or borrows an external resource. String and List hold returned data.
`View<Byte>` supplies non-owning binary output. Ordinary host failures return
Error. File cleanup remains explicit and normally uses `defer`.

V1 paths are ASCII-only. Files opened by `File.open` use binary C modes and
preserve exact bytes. The borrowed standard Files remain C text streams so
their newline behavior agrees with RFC 0030's `print` contract.

`Stream<T>` remains a separate lazy pull sequence. V1 File does not expose
line Streams, socket Streams, asynchronous I/O, or an in-memory output stream.

For brevity, code blocks that use `try` without showing an enclosing function
are function-body fragments. Their enclosing function must accept Error under
RFC 0029. `try` remains invalid at script or module scope.

## Goals

1. Read complete binary or UTF-8 data from a File.
2. Write complete byte Views or String payloads to a File.
3. Expose standard input, output, and error through the same operations.
4. Keep host failures recoverable where recovery remains meaningful.
5. Keep cleanup explicit, reliable, and compatible with existing `defer`.
6. Use one source API and primarily one C23 stdio backend on Windows and POSIX.
7. Preserve exact bytes without implicit newline or text conversion.

## Non-goals

V1 does not add:

- mutable Views or read-into-pointer APIs;
- partial or non-blocking reads and writes;
- read/write update streams;
- seek, tell, truncate, or file-size operations;
- line reading or formatted scanning;
- directories, metadata, permissions, or path normalization;
- full Unicode host paths;
- sockets, HTTP, TLS, subprocesses, pipes, or terminals;
- asynchronous I/O, polling, readiness, or cancellation;
- encodings other than UTF-8;
- an in-memory File, String builder, or general output-sink interface; or
- File-backed `Stream<T>` adapters.

## File modes

FileMode is a protected compiler-injected ADT with exactly three variants. The
following source-shaped declaration is descriptive; it does not appear in a
prelude module and users do not write it:

```seawitch
type FileMode =
| Read
| Write
| Append
```

The variants are qualified:

```seawitch
input: File = try File.open("input.txt", FileMode.Read)
output: File = try File.open("output.txt", FileMode.Write)
log: File = try File.open("app.log", FileMode.Append)
```

Their exact contracts are:

| Mode | C mode | Meaning |
|---|---|---|
| `Read` | `rb` | existing file, read only |
| `Write` | `wb` | create or truncate, write only |
| `Append` | `ab` | create if absent, write at the end |

Binary C modes are used on every platform. UTF-8 operations perform their own
validation; they do not rely on C text-stream translation.

`ReadWrite` is deferred until seek and update-stream transition rules are
specified. C update streams require subtle flush or positioning operations
between reads and writes, which are unnecessary for the initial API.

FileMode values may be copied, passed, returned, compared, and matched like
ordinary unit-variant ADT values. The File and FileMode type names cannot be
redeclared or shadowed. The variants exist only as qualified members, so an
unrelated local named `Read` remains valid.

## Protected built-ins and type-qualified forms

`File` and `FileMode` are protected built-in type names. `Stdio` is a protected
compiler-owned intrinsic qualifier. All three resolve before ordinary
declaration lookup, and a value, type, function, method owner, import, or module
qualifier cannot redeclare them.

`Stdio` is recognized only as the left side of the three exact calls below. It
is not a type, value, module, general namespace, generic argument, or runtime
object. It cannot be constructed, passed, stored, imported, matched, or used
with `size_of` or `align_of`. This adds no user-defined static-method or
namespace facility.

The compiler recognizes these type-qualified built-ins explicitly:

```text
File.open(String, FileMode)
Stdio.stdin()
Stdio.stdout()
Stdio.stderr()
```

`File.open` is a narrow built-in exception to RFC 0008's rule against
user-defined receiver-less type methods. The three Stdio-qualified calls are
equivalent protected intrinsic forms. They do not make general static methods
or namespaces available to user code. Their argument types, result types, and
lowering are fixed by this RFC, and the checker dispatches each form explicitly.

`FileMode.Read`, `FileMode.Write`, and `FileMode.Append` are ordinary qualified
ADT variant references under RFC 0022, not calls or static methods.

## File value and copying

File is a built-in small inline handle conceptually equivalent to:

```c
typedef struct sw_file {
    FILE *stream;
    sw_file_mode mode;
    bool owned;
} sw_file;
```

The representation is compiler-private, but it must not require a second heap
allocation merely to wrap `FILE *`.

File follows RFC 0035's C-style copying. Assignment, parameter passing, and
return copy the handle and continue to name the same C stream:

```seawitch
file: File = try File.open("data.bin", FileMode.Read)
alias: File = file
defer file.close()
```

Closing through one copy invalidates every other copy. Reusing or closing a
stale alias is programmer error. The compiler adds no reference count, owner
state, move state, or global open-file registry.

The mode field permits deterministic rejection of an incompatible operation.
The owned field distinguishes an opened File from a borrowed standard File.

### Type classification

File is a complete inline shallow-copyable value. It is valid anywhere another
complete inline value is valid, including as an object or ADT member, Array or
List element, Dict value, and View element. Copying any containing value copies
only the File handle. Container cleanup never closes a stored File:

```seawitch
files: List<File> = List<File>.new(h)
files.push(file)

files.free(h) // Frees List storage; does not close file.
file.close()  // External cleanup remains explicit.
```

File operations affect the external C stream and therefore do not require a
`mut` binding. `mut` is required only to reassign the File binding:

```seawitch
file: File = try File.open(path, FileMode.Write)
try file.write_text(text) // Valid on a fixed binding.

mut current: File = file
current = another         // Valid reassignment.
```

File has no literal, default value, `new`, equality, ordering, hashing, or
print formatting. It is not a Dict key. It follows RFC 0023's ordinary
truthiness rule and is therefore always truthy, including after programmer-
invalid cleanup; truthiness is not a resource-validity check.

The only valid initial File-producing operations are `File.open`,
`Stdio.stdin`, `Stdio.stdout`, and `Stdio.stderr`, plus ordinary copies and
values received from functions or containing values.

## Opening a File

```text
File.open(path: String, mode: FileMode): File | Error
```

The operation evaluates path and mode exactly once. Their relative evaluation
order follows RFC 0008 and is unspecified. It opens the host file immediately.
Failure returns Error and no File value:

```seawitch
fun load(h: Heap, path: String): String | Error
    file: File = try File.open(path, FileMode.Read)
    defer file.close()

    return file.read_text(h)
end
```

### V1 path contract

V1 accepts a non-empty, non-NUL ASCII String as a host path. Every payload byte
must be in `0x01..0x7F`.

```seawitch
File.open("notes/data.txt", FileMode.Read) // Valid v1 path.
File.open("", FileMode.Read)               // Error: empty path.
File.open("bad\0path", FileMode.Read)      // Error: embedded NUL.
File.open("café.txt", FileMode.Read)       // Error: non-ASCII v1 path.
```

When an invalid path is a literal, the checker reports it at compile time.
Otherwise `File.open` returns Error before calling C. Empty paths are rejected
by Seawitch rather than passed to implementation-dependent host behavior.

ASCII keeps `fopen` behavior representable through one implementation on
Windows and POSIX. Directory separators, case sensitivity, reserved names,
and path meaning remain host-defined. A future Path RFC may add UTF-8-to-UTF-16
Windows conversion and native POSIX byte paths without changing File's I/O
operations.

The trailing NUL already present in String storage is representation-only.
`File.open` first verifies that no embedded NUL occurs in the logical payload.

## Reading bytes

```text
file.read_bytes(heap: Heap): List<Byte> | Error
```

The operation reads from the current file position until EOF:

```seawitch
fun load_bytes(h: Heap, path: String): List<Byte> | Error
    file: File = try File.open(path, FileMode.Read)
    defer file.close()

    bytes: List<Byte> = try file.read_bytes(h)
    return bytes
end
```

EOF is successful. An empty remaining input produces an empty owning
`List<Byte>`. No EoS value is returned because this operation consumes the
entire remaining input in one call.

The caller is responsible for the successful List allocation:

```seawitch
bytes: List<Byte> = try file.read_bytes(h)
defer bytes.free(h)
```

If the host read fails after temporary storage has been allocated, the
operation releases that storage before returning Error. Partial input is
discarded and is not returned beside the Error.

Calling `read_bytes` through an ordinary File whose runtime mode is Write or
Append returns Error without invoking an incompatible C operation. A direct
`Stdio.stdin().read_bytes(h)` call is rejected at compile time because the
standard input stream retains C text-stream translation in v1.

## Reading UTF-8 text

```text
file.read_text(heap: Heap): String | Error
```

The operation reads from the current position to EOF, validates the complete
byte sequence as UTF-8, and creates one owning String result:

```seawitch
fun load_text(h: Heap, path: String): String | Error
    file: File = try File.open(path, FileMode.Read)
    defer file.close()

    text: String = try file.read_text(h)
    return text
end
```

An empty remaining input produces an owning empty String that the caller may
free normally. Malformed external UTF-8 returns Error and creates no String.

This recoverable behavior deliberately differs from
`String.from_bytes(heap, view)`, whose explicit conversion contract traps on
invalid UTF-8 under RFC 0044. File input is untrusted external data and is
expected to fail recoverably.

Allocation failure retains the existing Heap trap. It is not converted into an
I/O Error.

Calling `read_text` on Write or Append mode returns Error.

For a File opened through `File.open`, `read_text` validates the exact bytes in
the binary file. `Stdio.stdin().read_text` instead receives the bytes delivered
by the host C text stream, including any permitted host newline translation.

## Writing bytes

```text
file.write(bytes: View<Byte>): Nil | Error
```

The operation attempts to write the entire View:

```seawitch
bytes: View<Byte> = packet.slice(0, packet.length())
try file.write(bytes)
```

Success means every byte was accepted by the C stream and returns nil. Failure
returns Error. Bytes accepted before the failure remain written; File does not
provide transactional rollback.

The implementation loops over short C writes. It does not return a partial
Size because `Size | Error` cannot preserve both a partial count and its error.
Partial-write APIs are deferred for future sockets and non-blocking handles.

The View is borrowed only for the call and is never retained. An empty View is
a successful no-op.

Calling `write` through an ordinary File whose runtime mode is Read returns
Error without invoking an incompatible C operation. Direct binary writes on
`Stdio.stdout()` and `Stdio.stderr()` are rejected at compile time; standard
output remains a C text stream under RFC 0030.

## Writing text

```text
file.write_text(text: String): Nil | Error
```

The operation writes every logical UTF-8 payload byte:

```seawitch
try file.write_text("hello")
try file.write_text("\n")
```

It does not write String's trailing NUL, add a newline, translate line endings,
or convert the String to writable storage. Embedded NUL remains an ordinary
output byte.

`write_text` has the same full-write, partial-effect-on-error, opened-File mode,
and buffering rules as binary `write`. Its standard-File behavior differs as
specified below.

For a File opened through `File.open`, each String payload byte is written
unchanged because the File uses binary mode. `Stdio.stdout().write_text` and
`Stdio.stderr().write_text` submit the UTF-8 payload to the corresponding C text
stream; C may translate newline to the host line ending exactly as RFC 0030
permits for `print`.

## Flushing

```text
file.flush(): Nil | Error
```

Flush requests that the C runtime deliver pending output to its underlying
host handle:

```seawitch
try file.write_text(report)
try file.flush()
```

It does not promise durable storage on physical media. That requires a future
platform-specific synchronization operation.

Flush is valid for Write, Append, stdout, and stderr. Calling it on a Read File
returns Error rather than relying on implementation-defined C input flushing.

Flush on stdout or stderr participates in the shared standard-output gate
defined with RFC 0030. It cannot race the final shutdown flush.

## Closing

```text
file.close(): no value
```

Close is a cleanup operation and is normally deferred:

```seawitch
file: File = try File.open(path, FileMode.Write)
defer file.close()

try file.write_text(text)
try file.flush()
```

Close calls C `fclose`, including its final flush. A close failure produces a
fatal runtime trap:

```text
[Runtime Error] file close failed
```

It does not return Error. A recoverable close result would be discarded by an
ordinary deferred action and interacts unsafely with `errdefer` if C has
already closed a stream before reporting failure. Explicit recoverable
`flush()` handles expected output errors before cleanup; close never loses a
failure silently. A successful explicit flush does not prove that close will
succeed: a host filesystem may report a later resource or commit failure from
`fclose`. That residual case is intentionally fatal because cleanup cannot
return a recoverable Error through `defer` safely.

Closing a borrowed standard File traps before calling C. Double close and use
through an alias after close are programmer errors under RFC 0035 and need not
be detected reliably.

## Standard files

The protected Stdio intrinsic qualifier provides:

```text
Stdio.stdin(): File
Stdio.stdout(): File
Stdio.stderr(): File
```

They return borrowed File values with fixed modes:

- stdin is Read;
- stdout is Write; and
- stderr is Write.

Examples:

```seawitch
try Stdio.stdout().write_text("ready\n")
try Stdio.stderr().write_text("operation failed\n")

input: String = try Stdio.stdin().read_text(h)
```

Standard Files may be copied and used like other File handles but are never
owned by the program:

```seawitch
Stdio.stdout().close() // Compile error: direct borrowed standard File.
```

stdout and stderr may be flushed. Standard input reads to EOF and therefore is
not an interactive line-input facility. Standard Files are text-only in v1:

```seawitch
bytes: List<Byte> = try Stdio.stdin().read_bytes(h) // Compile error.
try Stdio.stdout().write(bytes)                     // Compile error.
```

The checker rejects an incompatible operation when its receiver is a direct
Stdio intrinsic because mode and ownership are statically known:

```seawitch
Stdio.stdin().write_text(text)  // Compile error: stdin is read-only.
Stdio.stdin().flush()           // Compile error: stdin is read-only.
Stdio.stdin().close()           // Compile error: standard File is borrowed.

Stdio.stdout().read_text(h)     // Compile error: stdout is write-only.
Stdio.stdout().write(bytes)     // Compile error: standard File is text-only.
Stdio.stdout().close()          // Compile error: standard File is borrowed.

Stdio.stderr().read_text(h)     // Compile error: stderr is write-only.
Stdio.stderr().write(bytes)     // Compile error: standard File is text-only.
Stdio.stderr().close()          // Compile error: standard File is borrowed.
```

This is a narrow direct-expression check, not File provenance analysis. Once a
standard handle is copied, passed, returned, or stored, ordinary runtime mode
and ownership checks remain responsible:

```seawitch
output: File = Stdio.stdout()
output.close() // Runtime Error: standard File is not owned.
```

Text-only standard Files preserve RFC 0030's C text-stream behavior and avoid
changing process-global Windows stream modes. Opened Files remain the exact
binary I/O facility.

No Seawitch module global is introduced. Each Stdio-qualified operation
produces a small File handle naming the C runtime's existing standard stream.

When RFC 0037's scheduler is linked, standard text writes and flushes use the
same process-wide scheduler-aware output lock and shutdown gate as `print`.
One `write_text` call is atomic relative to another standard `write_text` or
`print` emission. At shutdown, the gate closes after root defers, waits for an
in-flight operation, and then flushes stdout and stderr before C `main`
returns. No Seawitch standard-output operation begins after the gate closes.

Foreign C writes and other processes do not participate in this gate.

## Errors

Ordinary failures return the existing Error value:

```text
File | Error
List<Byte> | Error
String | Error
Nil | Error
```

V1 uses static portable Error headers and messages. It does not expose errno,
Windows error codes, or dynamically owned host error strings.

Representative messages are:

```text
could not open file
could not read file
could not write file
could not flush file
input is not valid UTF-8
operation is not permitted by the File mode
binary I/O is unavailable on a standard text File
path cannot be empty
path contains NUL
v1 path contains a non-ASCII character
```

The header is the Strand literal `"I/O Error"`. Compiler-owned I/O operations
populate Error's source file, line, and column from the Seawitch call site.

On Error, no success member is active. A failed read releases its temporary
allocation. A failed write may already have changed the external file, and its
Error does not imply rollback.

Cleanup traps, programmer-invalid aliases, and Heap allocation failure are not
converted into I/O Error values.

## Typical patterns

### Read text

```seawitch
fun read_config(h: Heap, path: String): String | Error
    file: File = try File.open(path, FileMode.Read)
    defer file.close()

    return file.read_text(h)
end
```

### Write text

```seawitch
fun write_report(path: String, report: String): Nil | Error
    file: File = try File.open(path, FileMode.Write)
    defer file.close()

    try file.write_text(report)
    try file.flush()
    return nil
end
```

### Append bytes

```seawitch
fun append_packet(path: String, packet: View<Byte>): Nil | Error
    file: File = try File.open(path, FileMode.Append)
    defer file.close()

    try file.write(packet)
    try file.flush()
    return nil
end
```

## File and Stream are separate

File is an eager external-resource API:

- it names a C/host resource;
- it can fail with host I/O Error;
- it reads all remaining input per read operation;
- it performs complete writes;
- it is explicitly closed; and
- calls may block.

`Stream<T>` is a lazy single-pass sequence:

- it produces one value per `next`;
- it ends with EoS;
- it has no file descriptor, path, encoding, flush, or close semantics; and
- it does not automatically own an external resource.

V1 adds no implicit conversion between them. A future File line or chunk
adapter must specify fallible Stream steps and keep the File alive explicitly.

## Builders, in-memory output, and HTTP

File I/O consumes existing String and byte values. It is not a String builder:

```seawitch
try file.write_text(already_built_text)
```

Small binary payloads may be assembled manually in `List<Byte>` and written
through a read-only View. Repeated String concatenation remains possible but
may allocate once per concatenation and is not proposed as an efficient
general builder.

A future `StringBuilder` or `ByteBuffer` should be an in-memory owning
collection with append operations and one final conversion:

```seawitch
builder: StringBuilder = StringBuilder.new(h)
defer builder.free(h)

builder.append("GET / HTTP/1.1\r\n")
builder.append("Host: example.com\r\n\r\n")
request: String = builder.to_string(h)
```

That type does not need File, close, flush, or host errors. It should be
specified only when repeated text construction is required.

This RFC can write an HTTP request to a File, but it cannot perform an HTTP
network request. Network transport requires a future Socket API; HTTPS also
requires TLS. HTTP request parsing, headers, framing, redirects, and response
handling belong in a library above sockets and byte/text buffers, not in core
File I/O.

## Concurrency

File operations are synchronous and may block the current RFC 0037 worker.
Scheduler-aware asynchronous I/O is deferred.

Copied File handles are not safe for unsynchronized concurrent use. Programs
must serialize shared access with an explicit Mutex or another specified
synchronization primitive. File adds no hidden lock for opened Files. The only
exception is the shared standard-output gate for Stdio.stdout, Stdio.stderr, and
`print`, which exists to make complete emissions atomic and shutdown safe.

## C23 lowering

- FileMode lowers to a small C enum.
- File lowers to a small struct containing `FILE *`, mode, and ownership flag.
- File copies and containing aggregate or collection copies remain ordinary
  shallow C struct copies; no generated cleanup walks stored File values.
- open uses `fopen` with `rb`, `wb`, or `ab` after path validation.
- reads loop with `fread` until EOF and distinguish EOF from `ferror`.
- writes loop with `fwrite` until complete or failed.
- flush uses `fflush` only on output Files.
- close uses `fclose` only on owned Files and traps on failure.
- String writes use `data` and `byte_length`, never `strlen`.
- all lengths, indices, and chunk counts use `size_t`.
- standard Files retain C text-stream mode on every platform; no process-global
  stream-mode mutation is emitted.
- standard text writes and flushes call the same output-gate helpers as RFC
  0030 when scheduler support is linked.
- no operation allocates a File wrapper, retains a View, or casts away String
  immutability.

Representative runtime results or traps are:

```text
Error: could not open file

Error: input is not valid UTF-8
Error: operation is not permitted by the File mode
```

The lexer and checker own literal and argument errors. Compiler-owned I/O

reach C generation.

## Acceptance criteria

This RFC is implemented when:

1. FileMode has exactly Read, Write, and Append with the stated binary modes;
2. File is a small shallow-copyable handle requiring no wrapper allocation;
3. open accepts only non-empty, non-NUL ASCII String paths and returns File or
   Error without passing an invalid path to C;
4. read_bytes returns an owning List<Byte> containing all remaining bytes;
5. read_text returns an owning valid UTF-8 String or Error;
6. failed reads release temporary storage and expose no partial success value;
7. byte and text writes complete fully or return Error with documented partial
   external effects;
8. writes retain no input View and never write String's trailing NUL;
9. flush is recoverable and output-only;
10. close returns no value, closes only owned Files, and traps on failure;
11. File has the exact inline, shallow-copy, storage, mutation, operator,
    truthiness, and explicit-cleanup classification stated above;
12. File, FileMode, Stdio, File.open, and the three Stdio-qualified operations
    have the exact protected built-in resolution rules stated above;
13. stdin, stdout, and stderr are borrowed text Files with fixed compatible
    modes; operations known to be invalid directly on a Stdio result fail at
    compile time, while the same invalid operations through a copied, stored,
    returned, or parameter File fail through the specified runtime checks;
14. opened Files preserve exact bytes across Windows and POSIX while standard
    Files preserve RFC 0030's C text-stream behavior;
15. standard text writes and flushes participate in RFC 0030's output lock and
    shutdown gate;
16. ordinary failures create source-located Error values with static portable
    messages;
17. all lengths and loop counters use Size and `size_t`;
18. File remains separate from Stream, builders, sockets, and HTTP; and
19. all invalid or unsupported cases fail closed before unsafe C operations.

## Implementation order

The I/O design is complete. Implement its prerequisite runtime facilities in
this order:

1. RFC 0044 finalizes and implements the canonical relationship between Byte,
   UInt8, String storage, and `View<Byte>`;
2. RFC 0029 implements the Error, `try`, and error-return contract used by every
   recoverable File operation; and
3. RFC 0030 implements the shared standard-output gate used by `print`,
   `Stdio.stdout()`, and `Stdio.stderr()`.

RFC 0031 Stream integration and RFC 0043 pointer-plus-length View construction
are coordination points, not prerequisites for this RFC.

## Final design contract

The v1 language surface, type classification, error behavior, cleanup model,
standard-stream coordination, and C23 lowering decisions are complete. No
further I/O design choice is open. No mutable View, offset type, ReadWrite mode,
platform-specific source API, builder, socket, or Stream integration is
required for v1. This RFC is Ready for Implementation; the prerequisite
features above are implementation sequencing, not unresolved design work.
