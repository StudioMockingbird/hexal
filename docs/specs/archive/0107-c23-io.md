# RFC 0107: C23 Byte-Stream I/O

- Kind: Feature Specification (Rust-Style RFC)
- Status: Closed; discarded in favor of RFC 0108
- Created: 2026-08-21
- Scope: synchronous byte input/output over C23 streams in compiled programs
- Coordinates with: RFC 0039 (C interop), RFC 0055 (filesystem/build driver),
  RFC 0091 (blocking calls), the Error and collection contracts,
  `docs/reference.md`, and `docs/status.md`
- Does not change: the core compiler's string-in/string-out boundary, String
  encoding, collection semantics, the scheduler, or the existing Error type

## Summary

Add one non-generic protected handle type:

```text
IO
```

`IO` is a synchronous C byte stream represented as one `FILE *` plus inline
direction and ownership fields. It owns no Hexal buffer, performs no text
decoding, allocates no wrapper, and introduces no OS-descriptor abstraction.

Initial operations:

```text
IO.stdin()  -> IO
IO.stdout() -> IO
IO.stderr() -> IO

IO.read(into: List<Byte>, max: Size) -> Size | EoS | Error
IO.write(from: View<Byte>)           -> Size | Error
IO.flush()                           -> Nil | Error
IO.close()                           -> Nil | Error
```

The API deliberately excludes opening paths, seeking, sockets, async values,
text operations, and buffering configuration. Those concerns do not need to
be solved to establish a small, useful byte-stream foundation.

## Design principles

1. Map to standard C23 before introducing an OS abstraction.
2. Add no language concept when an existing Hexal type expresses the contract.
3. Expose partial transfers rather than hiding them in mandatory loops.
4. Keep allocation and buffering explicit.
5. Keep filesystem names and socket addressing outside byte-stream semantics.
6. Use modern C23 facilities only where they implement a real requirement;
   novelty alone is not a reason to emit a feature.

## Why `FILE *`

C23 standardizes one portable open-stream abstraction: `FILE *`.

Using it gives Hexal:

- files, pipes, terminals, and standard streams through one C type;
- portable transfer through `fread` and `fwrite`;
- portable flushing and closing through `fflush` and `fclose`;
- EOF/error distinction through `feof` and `ferror`;
- direct adaptation to C libraries using `FILE *`;
- no POSIX/Windows split in signatures or generated runtime code; and
- coherent interaction with `print`, which already writes through `stdout`.

A raw descriptor is not a C23 abstraction. POSIX descriptors, Windows
`HANDLE`, and Windows `SOCKET` are different APIs. Collapsing them into
`intptr_t` creates a platform runtime before Hexal needs one and still does not
describe ownership, pollability, buffering, or capability.

This RFC chooses portability and direct C interoperation over an unbuffered
descriptor floor. A later socket API is a separate type rather than an `IO`
pretending every handle is interchangeable.

## Type and representation

`IO` is a protected nominal handle. Generated C uses a small inline descriptor:

```c
enum hex_io_capability : uint8_t {
    HEX_IO_READ  = 1,
    HEX_IO_WRITE = 2,
};

typedef struct hex_io {
    FILE *stream;
    enum hex_io_capability capability;
    bool owned;
} hex_io;
```

Rules:

- A valid `IO` has a non-null stream.
- Assignment, arguments, and returns copy the descriptor. Copies alias one C
  stream and its position, buffering, EOF/error indicators, and lifetime.
- Exactly one initial capability is present: read or write. Update streams are
  excluded because portable C stdio imposes sequencing rules between input and
  output that require shared direction state across aliases.
- Capability prevents calling C with the wrong stream direction. A mismatch
  returns Error without invoking stdio.
- The ownership bit controls close. It does not implement reference counting
  or unique ownership.
- Closing through one alias invalidates every alias, following Hexal's existing
  external-state rule.
- Direct same-binding use after close and repeated close are rejected wherever
  existing local flow analysis proves them.
- Aliases escaping through parameters or another binding remain under the
  existing undecided-lifetime envelope. This RFC adds no move semantics,
  borrow checker, reference count, or runtime registry.
- Initially IO is valid in bindings, parameters, results, and as a direct union
  member so `IO | Error` construction works. It is rejected in object/ADT
  members, collections, Tasks, Channels, pointees, heap allocation, and every
  aggregate or container recursively containing IO. This prevents accidental
  long-lived aliases without adding an ownership system.

The representation is a plain C value with one pointer and two small fields.
There is no wrapper allocation, global registry, vtable, or indirect dispatch.

## Standard streams

```text
IO.stdin()  -> IO
IO.stdout() -> IO
IO.stderr() -> IO
```

- They lower to inline descriptors over C `stdin`, `stdout`, and `stderr`.
- They are infallible under this RFC's hosted C23 target.
- They return borrowed process streams.
- stdin carries read capability; stdout and stderr carry write capability.
- All three carry `owned = false`; close traps before calling `fclose`.
- `flush()` on stdin returns capability Error without calling `fflush`.

Foreign `FILE *` bindings must state one direction and owned/borrowed status
under RFC 0039. Wrapping creates the inline descriptor without allocation.
Read/write update streams are not importable as IO in the initial surface.

## Construction boundary

This RFC does not open paths.

- Opening belongs to the filesystem/core-library proposal.
- That proposal returns `IO | Error` after settling path encoding, embedded
  NUL, modes, creation, permissions, and platform behavior.
- RFC 0039 may import a C function returning `FILE *` once ownership is known.
- The core compiler never reads or validates a host path.

This keeps IO usable for standard streams, pipes, temporary C streams, and
foreign libraries without making every stream a filesystem object.

## Read

```text
IO.read(into: List<Byte>, max: Size) -> Size | EoS | Error
```

- `into` is an existing reusable byte buffer. Read appends; it never clears or
  replaces existing bytes.
- Missing read capability returns Error before allocation or `fread`.
- `max` is the maximum number of bytes appended by this call.
- `max == 0` returns `Size(0)` without touching the stream or allocating.
- The List reserves checked capacity for `old_length + max`, then performs at
  most one `fread(data + old_length, 1, max, stream)`.
- A positive return is the exact number appended. A short positive read is
  ordinary success, including when EOF or an error followed those bytes.
- Zero with the EOF indicator set returns `eos`.
- Zero with the error indicator set returns Error and calls `clearerr`, allowing
  an explicit retry.
- Zero with neither indicator is Error; the runtime never invents EOF without
  `feof` evidence.
- List allocation and growth rules remain authoritative. Capacity overflow or
  allocation failure traps as List growth does today.
- Receiver, List, and max evaluate once, left-to-right.

The newly appended region is:

```text
into.slice(into.length() - count, into.length())
```

No mutable View, uninitialized Array, const generic, pointer arithmetic, or
unsafe pointer/count pair is added.

## Write

```text
IO.write(from: View<Byte>) -> Size | Error
```

- `from` is a borrowed read-only byte range.
- Missing write capability returns Error before `fwrite`.
- An empty View returns `Size(0)` without calling `fwrite`; no null pointer is
  passed with zero count.
- A non-empty View performs at most one `fwrite(data, 1, length, stream)`.
- The returned Size is the exact byte count accepted by the C stream.
- A short positive write is ordinary success. The caller decides whether to
  retry the unwritten suffix.
- Zero for a non-empty View returns Error. `clearerr` runs before return so an
  explicit retry is possible.
- Write does not flush.
- Receiver and View evaluate once, receiver first.

String output composes explicitly:

```text
output.write(text.bytes())
```

IO moves bytes. It performs no implicit String/C-string conversion and no UTF-8
validation.

## Flush and close

```text
IO.flush() -> Nil | Error
IO.close() -> Nil | Error
```

- Flush requires write capability, then calls `fflush`; success returns nil and
  failure returns Error.
- Close requires `owned = true`, then calls `fclose`; borrowed close traps.
- Close invalidates the IO even when `fclose` reports failure: C may already
  have released resources, so close is never retried.
- Cleanup expressions may discard these results under existing cleanup rules.
- There is no `is_closed`, `is_eof`, or `has_error`. Completion comes from read,
  failures are returned, and locally proven closed use is rejected.

## Errors

I/O failures use existing `Error` and therefore compose with `try` and
`errdefer` without another result abstraction.

Portable errors carry:

- the Hexal source location of the call;
- header `"IO Error"`; and
- `"read failed"`, `"write failed"`, `"flush failed"`, or `"close failed"`.

Capability mismatch uses `"stream is not readable"` or
`"stream is not writable"`; it is recoverable Error rather than a trap because
the same function may receive streams created by different environments.

C23 does not require stdio failures to set `errno`. This RFC does not promise
errno or locale-dependent `strerror` text and allocates no dynamic String on an
error path. A target-specific filesystem or foreign binding may expose richer
errors separately.

## Blocking and Tasks

The surface is synchronous and blocking-looking.

Initial lowering calls stdio on the current worker. A blocking operation blocks
that OS worker. Other workers continue; if all workers block, the scheduler
stalls until one call completes.

This resolves RFC 0091 as its accept-the-block option for C23 IO. A later
blocking pool may park the Task and perform the same call elsewhere without
changing any IO signature.

One IO must not be used concurrently by multiple Tasks without an external
Mutex. This RFC promises no cross-task ordering or compound-write atomicity.

## Relationship to `print`

`print` remains on C stdio and shares buffering and ordering with
`IO.stdout()`.

- This RFC does not rewrite print to raw descriptors.
- Both surfaces target the same underlying `FILE *`.
- `IO.stdout().flush()` flushes pending stdout output.
- Normal hosted-program termination retains C stream flushing.

Keeping both on stdio avoids mixing `fwrite(stdout)` with
`write(fileno(stdout), ...)`.

## Generated C23 contract

Demanded programs emit `hexal/io.h` and `hexal/io.c`.

`hexal/io.h`:

- includes `hexal.h`, `hexal/list.h`, `hexal/view.h`, and `<stdio.h>` directly;
- defines the fixed-width C23 direction enum and inline `hex_io` descriptor;
- declares internal read/write/flush/close support;
- uses `[[nodiscard]]` on support functions whose result is translated into a
  Hexal success/Error union; and
- contains no platform branch, descriptor typedef, or OS header.

`hexal/io.c`:

- includes `hexal/io.h` first;
- uses `fread`, `fwrite`, `fflush`, `fclose`, `feof`, `ferror`, and `clearerr`;
- uses `<stdckdint.h>` `ckd_add` and `ckd_mul` for capacity/byte arithmetic;
- uses C23 `nullptr` for internal empty-storage sentinels where required;
- never passes a null pointer to `fread` or `fwrite`;
- adds no wrapper that merely delegates to one expression; and
- returns an internal status/count record. Module-local inline adapters convert
  it to each structural Hexal result union, because those wrappers are
  module-owned.

IO demand also selects one internal `List<Byte>` reserve helper in
`hexal/list.h`. It accepts a minimum capacity, reuses the List's stored
allocator, and shares the existing checked growth/allocation path. IO must not
copy List allocation logic into `io.c`, grow by repeated single-element pushes,
or expose `reserve` as a new source method in this RFC.

No `static_assert` is emitted: `FILE *`, `size_t`, `uint8_t`, and `bool` add no
target assumption beyond the supported C23 contract. No `constexpr`, `typeof`,
`_Generic`, or builtin is used without a requirement it uniquely satisfies.

## Compiler architecture

- IO is a protected core-library handle until RFC 0039 can express the binding.
- Parsing adds no syntax or AST node.
- The checker registers one type and its operations, applies placement rules,
  checks exact types, and reuses closed-state flow facts.
- The generator uses ordinary checked-call metadata and demand-selects IO.
- The component owns C support; module adapters own structural-union injection
  and source-location Error construction.
- Programs without IO emit no IO artifact and stay byte-identical.

## Validation

This section is exhaustive for the initial implementation.

- IO has exactly the Summary signatures; `IO<T>` is rejected.
- IO is accepted in bindings, parameters, results, and direct unions and
  rejected in every initially excluded position.
- Standard streams lower to the exact borrowed capability descriptors.
- Read/write/flush capability mismatch returns Error without issuing stdio.
- Closing a standard stream reaches the specified trap before `fclose`.
- Read preserves prior List bytes, appends at most max, reports positive short
  reads as Size, proven EOF as EoS, and failure as Error.
- `read(buffer, 0)` performs no allocation or C call.
- Read capacity arithmetic uses `ckd_add`/`ckd_mul`; no unchecked equivalent
  survives.
- IO reuses the one internal List reserve path; no second List allocator or
  growth formula appears in `io.c`.
- Write accepts exactly View<Byte>; String requires `.bytes()`.
- Empty write performs no C call; non-empty write reports the exact count and
  treats a positive short write as success.
- Flush and close return `Nil | Error`; cleanup uses ordinary cleanup rules.
- Direct use after close and repeated close reject; undecidable aliases remain
  accepted under the existing external-state envelope.
- Program support is emitted once; module adapters create correct local result
  unions without duplicate external symbols.
- `io.h` has exact dependency order; declarations precede uses; absent demand
  emits no IO artifact.
- Generated C uses C23 stdio, not POSIX/Windows descriptor APIs or `fileno`.
- Print stays on `fwrite(stdout)` and alone selects no IO component.
- Repeated compilation produces byte-identical artifacts.
- The snippet manifest gains only new IO snippets.
- `docs/reference.md` is updated only after acceptance and stabilized behavior;
  it records surface, blocking, alias/lifetime, and C23 lowering once each.
- `go test ./...`, `go vet ./...`, and `go vet -tags c23 ./...` pass without an
  external compiler.

Runtime transfer, EOF, flush, and close remain a generated-C coverage gap until
the toolchain lifecycle can execute artifacts. Text assertions are mandatory
and do not claim runtime proof.

## Non-goals

- Filesystem paths, modes, directories, metadata, or permissions.
- Sockets, addressing, polling, timeouts, readiness, or half-close.
- Seeking or file-position values.
- Text readers/writers, line iteration, formatting, scanning, or decoding.
- Buffer configuration, implicit write-all/read-exact loops, or memory streams.
- Mutable View, uninitialized Array, const generics, interfaces, type erasure,
  async/await, or coroutines.
- Native error codes or locale-dependent `strerror` text.
- Compiler filesystem access or ordinary tests invoking external tools.

## Drawbacks

- C stdio buffering is less explicit than a raw descriptor.
- A blocking call can occupy a scheduler worker.
- Read buffers are heap-backed Lists; stack byte buffers require a future safe
  writable-span design rather than an unsafe pointer/count API.
- The initial surface cannot seek.
- Standard streams are borrowed but share the source type with owned streams;
  the inline ownership bit makes close enforce the distinction.
- Portable Error reports the operation, not a native error code.

These costs buy a smaller compiler and runtime: one thin standard-stream
descriptor, seven stdio operations, no platform branch, no handle union, no
scheduler integration, and no new general language feature.

## Open decisions

1. **Name:** `IO` or `File`. Recommendation: `IO`; pipes and standard streams
   are not filesystem files.
2. **Read buffer:** existing `List<Byte>` plus max, or block on mutable View.
   Recommendation: List; it is bounds-safe and exists today.
3. **Standard close:** trap or return Error. Recommendation: trap; closing
   borrowed process state violates the contract rather than encountering an
   environmental failure.
4. **Blocking:** accept one blocked worker initially or require a pool.
   Recommendation: accept and document it; a pool changes no source surface.

## Readiness

Not implementation-ready until those four decisions are accepted and C-interop
ownership is either specified or explicitly deferred to protected support.

Once accepted, this RFC replaces RFCs 0065, 0105, and 0106 rather than
coexisting as a fourth IO direction.
